# Dependency updates

Updates land on `deps` without a human and reach `main` through one reviewed
pull request. The pipeline is the one the other six repositories of this account
run; its design rationale and porting checklist live in
`QA-web-labprojects-python` (`docs/dependency-updates.md`,
`docs/porting-the-dependency-pipeline.md`). Only what is specific here is below.

```
Dependabot ─▶ PR into deps ─▶ CI ──green on this exact commit──▶ squash-merged into deps
                                                                       │
                                          promotion PR deps → main (CI runs on the result)
                                                                       │
                                                         ◀ maintainer merges (squash) ▶
                                                                       ▼
                                                                      main
                                                                       │
                                                  deps re-cut from main ┘
```

## Branch contract

| Branch | Who writes | History |
|---|---|---|
| `main` | pull requests only, merged by the maintainer | |
| `deps` | bots only | **disposable**, re-cut from `main` after every promotion |

`deps` is never merged into — it is reset. Every commit on it is a bot commit,
and a reset bot commit is regenerated by Dependabot's next scan, so the branch
holds nothing worth a merge. The guard in `deps-promote.yml` keeps that true:
one non-bot commit on `deps` and the workflow resets nothing and opens a
*Dependency promotion is blocked* issue, which it closes itself on the first run
that is not blocked. `deps` is the one branch without an author namespace — it
belongs to the pipeline, not to a person (`docs/CONVENTIONS.md`).

The promotion pull request is titled by the workflow and squash-merged by the
maintainer, like every pull request into `main` that is not a phase. After it
merges, an open phase branch takes the new `main` the usual way: a pull request
merging `main` into it, as a merge commit (`docs/CONVENTIONS.md`, "Merging").

## Schedule, groups and exceptions

Monthly. Per ecosystem, one pull request for every minor and patch bump and one
per major. Two families are grouped across all update types, because their
members demand each other's versions and bumped one at a time they leave a queue
that cannot drain:

- **`ef-core-and-npgsql`** — `Microsoft.EntityFrameworkCore*`, `Npgsql*`,
  `Pgvector*`. The provider's major follows EF Core's, and the pgvector mapping
  follows the provider. No version cap: the project already targets `net10.0`.
- **`react`** — `react`, `react-dom` and their `@types`. A lone `react-dom` bump
  broke a build in Webdev.

One exception: **`Microsoft.OpenApi` majors are ignored.**
`Microsoft.AspNetCore.OpenApi` 10.0.x requires `Microsoft.OpenApi < 3.0.0`
(NU1608), and with 3.x its source generator fails to compile (`CS0200`,
measured on PR #21). Remove the `ignore` when an AspNetCore.OpenApi release
accepts version 3.

`security-audit.yml` reports advisories for NuGet (transitive included) and for
`src/Web` (npm, high and above) into the run summary every Monday; it never
fails and never opens an issue. Dependabot security updates are switched off:
they target `main` directly and would bypass `deps`.

## Why CI needs no change

`build.yml` runs on `push: [main]` and on `pull_request:` with no branch or path
filter, so a pull request into `deps` is built and a push to `deps` is not. The
gate reads the `pull_request` run of each Dependabot pull request, and the
promotion gets its own run on the combined result.

Two values in the gate have to match this repository: the workflow's **name**
(`Build`) in the `workflow_run` trigger, and its **filename** (`build.yml`) in
`CI_WORKFLOW`. Get either wrong and nothing reports an error — the gate never
fires. CI fails on the first failing command and retries downloads (PR #25);
before that a failed `dotnet build` could pass as green, and the gate would
have merged it.

## Repository settings this depends on

1. **Secrets and variables → Actions**: `DEPS_PAT`, a token with Contents, Pull
   requests, Actions and Workflows read+write on this repository. Without it
   both automation workflows fail with 401.
2. **Actions → General → Workflow permissions**: *Allow GitHub Actions to create
   and approve pull requests* — ticked.
3. **General → Pull Requests**: squash merging enabled.
4. **Dependabot alerts** enabled, **Dependabot security updates** disabled.
5. **Rulesets** on `main` and `*/phase-*` (`docs/REPOSITORY.md`). Neither covers
   `deps`, which the promotion has to be able to reset.

## Running it by hand

```
Actions → Dependency promotion → Run workflow   # creates or realigns deps, opens the promotion PR
Actions → Dependency auto-merge → Run workflow  # sweeps; one log line per open update
```

The first run of *Dependency promotion* creates `deps` from `main`. An update
job does not start from a manifest change alone: *Insights → Dependency graph →
Dependabot → Check for updates* on one manifest row triggers one.
