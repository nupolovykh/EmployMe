# Naming Conventions

Derived from this repo's git/GitHub history (branches, commits, PRs, issues) as of 2026-08-27.

Where two styles competed, **the author's own commits decide** — not whichever style is most
recent, and not whichever a generated commit happened to use. An earlier draft of this file got
that backwards: it counted a run of Claude-generated commits as the current convention and filed
the author's own `EM-<n>:` prefix under "legacy". Recency is not authority here.

Every ticket number below is a Linear issue in team `EM` (see `docs/PLAN.md` §01 — Linear holds the
work items, this repo's docs hold the plan and the evidence).

## Branches

Two namespaces are in active use, chosen by who/what is creating the branch:

- **`claude/<slug>`** — branches created by a Claude Code session (interactive or background).
  `<slug>` is a short kebab-case description of the scope, usually a phase or feature
  (`claude/phase-1-vacancies-api`, `claude/phase-0-api-foundation`). Background/parallel sessions
  may get a random 6-character suffix appended automatically for collision-avoidance
  (`claude/devcontainer-setup-s1a15o`) — that suffix is generated by the tooling, not hand-chosen.

- **`polovykh/<slug>`** — branches owned by the author. `polovykh` is the fixed personal
  namespace (not the GitHub login, which is `nupolovykh`), and the same name Linear uses in the
  branch names it suggests. The slug takes one of two shapes:

  - `em-<n>-<short>` when the branch serves one Linear ticket
    (`polovykh/em-51-sources-schema-rebuild`, `polovykh/em-56-plan-sync`). Keep it short —
    ticket #51's branch was first pushed with the whole ticket title as the slug
    (`polovykh/em-51-rebuild-the-sources-schema-rows-with-compliance-columns-not`) and was
    superseded by the shorter form in the next PR for the same ticket.
  - a phase or feature slug when the branch spans several tickets and no single one names it
    (`polovykh/phase-1-vacancies-api`). Naming such a branch after one of its ten tickets would
    be less accurate than not naming a ticket at all.

  Until 2026-09-29 this namespace was `devpolovykh/`. The branches were renamed on GitHub, but
  merge commits and closed pull requests from before that date keep the old name, because
  rewriting them would mean rewriting published history.

Authorship is about who owns the branch, not who typed into it. A branch the author drives stays
under `polovykh/` however much of the work a Claude session did on it; `claude/` is for branches
a session opened on its own.

**Phase branches and ticket branches.** A phase is built on its own branch,
`<namespace>/phase-<n>-<slug>` (`polovykh/phase-2-reliability`), cut from `main` when the phase
starts. Each ticket in it gets a branch of its own, `<namespace>/em-<n>-<short>`, cut from the
phase branch and merged back into it through a pull request. `main` receives the phase as a
whole, once its exit criterion is met — see "Merging" under Pull requests. Any namespace may own
a phase branch; the `phases` ruleset in `docs/REPOSITORY.md` protects them all alike.

**Every branch carries its author namespace — there are no bare names.** A branch called
`phase-1-rebuild` or `em56-plan-sync` says nothing about who owns it, and both forms show up in
this history only as mistakes that were renamed before they went anywhere. The namespace comes
first, always, from the moment the branch is created — not added later "before pushing". A local
throwaway is still `claude/<slug>` or `polovykh/em-<n>-<slug>`.

The one exception is `deps`: it belongs to the dependency pipeline, not to a person, only bots
write to it, and it is reset after every promotion — see `docs/dependency-updates.md`.

## Commits

**The ticket leads the subject line.** `EM-<n>: <summary>`, or `EM-<n>, EM-<m>:` when a commit is
scoped to more than one, and `EM-<n>–<m>:` for a contiguous run. Summary in the imperative, no
trailing period:

```
EM-52: add IJobSource abstraction and source-agnostic ingest
EM-52, EM-53: record what the four adapters actually returned
EM-45–49: run all five Phase 0 spikes, close the source-qualification gate
```

Reading `git log --oneline` should answer "which ticket is this?" in the first token, without
scanning to the end of each line. A trailing `(EM-<n>)` does not survive truncation in GitHub's
commit list or in a narrow terminal, which is exactly where the ticket is most needed.

Maintenance/infra commits with no corresponding ticket carry no `EM-` prefix; they take `Chore:`
instead, below. Apart from merge commits and Dependabot's own, `Initial commit` is the only commit
on `main` with neither.

**Unplanned work not tied to any phase** — config, assistant/tooling rules, process docs like this
one — has no ticket to lead with, so `Chore:` takes that slot instead. Same position, same purpose:
the first token says what kind of commit this is.

```
Chore: add commit-message-length rule to CONVENTIONS.md
```

**Keep the whole message on one screen.** Subject plus body should read without scrolling in
`git show` or GitHub's commit view — roughly 20-25 lines, body wrapped at ~72 chars. The original
EM-46 Lever re-run commit, `48b5af5`, is the counter-example: several screens long. `main` now
carries a condensed version of it, and the original stays reachable from PR #13. If a change
genuinely needs more explanation than that, put the rest in the PR
description or in `docs/ASSUMPTIONS.md`/`docs/SOURCES.md` and link it from the commit — don't cram
it into the commit body.

A run of Claude-generated commits used a trailing `(EM-<n>)` instead
(`Add IJobSource abstraction and source-agnostic ingest (EM-52)`). That form is being retired, not
tolerated as a second live convention — rewrite it to the prefix form whenever a branch carrying it
is rebuilt.

**Gaps found while a phase is still unmerged.** If you're working a phase whose branch has never
landed on `main` yet, and you spot something that phase's own earlier work missed, don't open an
issue for it — add a follow-up commit on the same branch, marked `Fix:` the way unplanned work is
marked `Chore:`. The ticket follows the marker, separated by a dash; a fix with no ticket behind it
simply omits that part:

```
Fix: EM-53 - Greenhouse timestamps not normalized to UTC before persist
Fix: dev-server proxy dropped the query string on /api/vacancies
```

**A review round on an open PR.** A round of review on a PR that has not merged is answered by one
commit carrying `PostReview:`, with the ticket list after the marker in the same shape `Fix:` uses:

```
PostReview: EM-15, EM-16, EM-52, EM-59 - post-review pass on PR #15
```

Separate from `Fix:` deliberately. `Fix:` is a gap the author found while working the phase;
`PostReview:` answers someone else's review, so its reader is a reviewer checking whether their
findings were addressed, and the body owes them which were fixed and which were deferred and why.
**One commit per round, not one per finding.** A round answered across six commits is what makes a
branch read as churn — PR #15's first round was answered that way and produced two commits that a
later one erased whole.

Both markers are commits on a ticket branch. When the ticket's PR is squashed into the phase
branch they fold into its one commit, and the PR keeps them individually for the reviewer. A gap
found after the ticket has already been squashed gets a short branch and PR of its own into the
phase branch, and its squash commit keeps the `Fix:` subject.

`Fix:`, `Chore:` and `PostReview:` are the only three markers that displace the ticket from the
first position, and all three do it for the same reason — the kind of commit is what you scan for.
Everything else leads with `EM-<n>:`. The ticket is whichever one the miss belongs to. The phase is
still in flight, so the fix travels with it instead of becoming separate backlog. Once the phase
has merged, this option is gone — see "Gaps found after a phase has merged" under GitHub Issues.

Body (when there is one) explains **why**, not what — matches this repo's own commit-message
instruction in the personal CLAUDE.md. In this history the why is almost always evidence: what was
tried, what broke, what was verified live and how (`docs/PLAN.md` §01 rule 1, "evidence over
assertion"). A `Verified ...` line describing an actual run against dev Postgres, a live endpoint,
or a built app is the norm for anything non-trivial, not an afterthought.

Merge commits keep git/GitHub's default message (`Merge branch 'x' into y`,
`Merge pull request #N from <owner>/<branch>`), sometimes with an added paragraph noting how a
conflict was resolved. They occur in two places only: a phase landing on `main`, and `main` being
merged into a phase branch to bring it up to date. Everything else arrives as a squash commit.

Claude Code-authored commits carry:
```
Co-Authored-By: Claude <model name> <noreply@anthropic.com>
Claude-Session: https://claude.ai/code/session_<id>
```
Leave these on commits Claude actually authored; don't add them to commits you write yourself.

## Pull requests

**A phase PR**, the phase branch into `main`, is titled `Phase <phase>: EM-<tickets> <summary>`
where `<phase>` matches a `docs/PLAN.md` roadmap phase (`Phase 0`, `Phase I`, `Phase II`, ...).
The phase leads because it is the PR's scope; the tickets follow immediately, ahead of the prose,
for the same reason they lead a commit subject:

```
Phase 0: EM-45–51 rebuild sources schema, close Phase 0 spike gate
Phase I: EM-11, EM-15, EM-16 vacancies API, filters, frontend
```

A trailing `(EM-11, EM-15, EM-16)` appears on the earlier PRs; retire it the same way as the
trailing commit form.

**A ticket PR**, a ticket branch into its phase branch, is titled exactly like the commit it will
become, because squashing turns the title into that commit's subject and GitHub appends ` (#N)`.
Any other PR into `main` that a person opens — `Chore:` work — is titled the same way. Pull
requests the dependency pipeline opens keep the titles it gives them:

```
EM-20: put every upstream fetch behind a Polly resilience pipeline
Fix: EM-22 - the host refused to start without a DSN
```

### Merging

| Pull request | Into | Merged as |
|---|---|---|
| ticket, or a `Fix:` after the ticket landed | its phase branch | squash |
| `main`, to bring the phase up to date | a phase branch | merge commit |
| phase | `main` | merge commit |
| Dependabot update | `deps` | squash, by the pipeline once CI is green |
| dependency promotion, `deps` → `main` | `main` | squash |
| anything else | `main` | squash |

The method follows from the kind of pull request; it is never chosen at merge time. A phase lands
as a merge commit so each ticket's squash commit reaches `main` intact, and `git log --oneline
main` still answers "which ticket is this?" commit by commit. Bringing `main` into a phase branch
is a merge for a different reason: a squash would copy `main`'s changes as a new commit git cannot
recognise, and the phase would later deliver them to `main` a second time — conflicting in exactly
the lockfiles both sides touch.

When squashing, trim GitHub's default body (every commit message on the branch) to the one-screen
rule; the individual commits stay on the pull request. A pull request is merged by the maintainer,
or on the maintainer's explicit go-ahead for that pull request — see the hard rules in
`CLAUDE.md`.

Two early PRs (#1, #7) used a `DEMO:` prefix ahead of throwaway/demo submissions for branches that
were later reopened properly (#2, #6) — not a convention to continue, just how those two got
superseded.

## GitHub Issues

Used rarely — Linear is the actual backlog (`docs/PLAN.md`: "Linear holds the work items"). The two
GitHub issues in this repo's history exist only to mirror a specific Linear ticket into GitHub's
UI, titled `EM-<n>: <description>` matching the Linear ticket's own title, with GitHub's stock
labels (`bug`, `documentation`, `help wanted`, etc.) applied by nature of the work — **no custom
label scheme on issues.** Pull requests are the other way round: they carry the `area/*` / `type/*`
taxonomy in `.github/labels.yml`, because they are what actually gets filtered. Don't create a
GitHub issue as a substitute for a Linear ticket; only mirror one over if there's a specific reason
(e.g. surfacing it for portfolio visibility).

**Gaps found after a phase has merged.** If the miss belongs to a phase that has already landed on
`main` — no branch left to fix forward on — open a GitHub issue for it (`EM-<n>: <description>`,
same as any mirrored ticket), and name the phase it actually belongs to in the body (e.g. "Belongs
to Phase 0"), since the title alone won't show that once it's sitting in GitHub's current issue
list next to whatever phase is active now. This is the counterpart to "Gaps found while a phase is
still unmerged" under Commits — which of the two applies turns on whether that phase's branch has
ever been merged into `main`, not on when the gap was found.
