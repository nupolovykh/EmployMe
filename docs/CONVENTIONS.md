# Naming Conventions

Derived from this repo's actual git/GitHub history (branches, commits, PRs, issues) as of
2026-08-27, not imposed from outside. Where two styles competed, the one used in the most recent
commits wins here; the older style is noted as legacy so it's recognizable, not repeated.

Every ticket number below is a Linear issue in team `EM` (see `PLAN.md` §01 — Linear holds the
work items, this repo's docs hold the plan and the evidence).

## Branches

Two namespaces are in active use, chosen by who/what is creating the branch:

- **`claude/<slug>`** — branches created by a Claude Code session (interactive or background).
  `<slug>` is a short kebab-case description of the scope, usually a phase or feature
  (`claude/phase-1-vacancies-api`, `claude/phase-0-api-foundation`). Background/parallel sessions
  may get a random 6-character suffix appended automatically for collision-avoidance
  (`claude/devcontainer-setup-s1a15o`) — that suffix is generated by the tooling, not hand-chosen.

- **`devpolovykh/em-<n>-<slug>`** — branches created by the author for a specific Linear ticket.
  `devpolovykh` is the fixed personal namespace (not the GitHub login, which is `nupolovykh`).
  `<n>` is the Linear ticket number, lowercase `em-` prefix attached
  (`devpolovykh/em-51-sources-schema-rebuild`, `devpolovykh/em-56-plan-sync`). Keep `<slug>` short —
  ticket #51's branch was originally pushed with the full ticket title as the slug
  (`devpolovykh/em-51-rebuild-the-sources-schema-rows-with-compliance-columns-not`) and was
  superseded by the shorter form in the next PR for the same ticket.

Local-only scratch branches without either prefix show up in this history
(`em56-plan-sync`, `phase0-em46`) but were renamed to the `devpolovykh/em-<n>-...` form before
push. Fine to use a bare short name while a branch never leaves your machine; give it the full
prefixed name before pushing or opening a PR.

## Commits

`<Imperative summary, no trailing period>` optionally followed by `(EM-<n>)` or
`(EM-<n>, EM-<m>)` when the commit is scoped to one or more specific tickets:

```
Add IJobSource abstraction and source-agnostic ingest (EM-52)
Record what the four adapters actually returned (EM-52, EM-53)
```

Maintenance/infra commits with no corresponding ticket omit the parenthetical entirely
(`Add dependabot config for nuget dependency updates`, `Initial commit`).

**Unplanned work not tied to any phase** — config, assistant/tooling rules, process docs like this
one — gets a `Chore: ` prefix and no `(EM-<n>)`, same as existing untracked infra commits:

```
Chore: add commit-message-length rule to CONVENTIONS.md
```

**Keep the whole message on one screen.** Subject plus body should read without scrolling in
`git show` or GitHub's commit view — roughly 20-25 lines, body wrapped at ~72 chars. EM-46's
"Re-run the Lever spike against the target-company registry" commit is the counter-example: several
screens long. If a change genuinely needs more explanation than that, put the rest in the PR
description or in `docs/ASSUMPTIONS.md`/`docs/SOURCES.md` and link it from the commit — don't cram
it into the commit body.

A handful of older commits used `EM-<n>: <summary>` as a prefix instead
(`EM-50: record Sezzle as a rejected target company`). Every commit from EM-52 onward uses the
`(EM-<n>)` suffix form — treat the prefix form as legacy, not a second live convention.

**Gaps found while a phase is still unmerged.** If you're working a phase whose branch has never
landed on `main` yet, and you spot something that phase's own earlier work missed, don't open an
issue for it — add a follow-up commit on the same branch, prefixed `Fix: `:

```
Fix: normalize Greenhouse timestamps to UTC before persist (EM-53)
```

The ticket ref still points at whichever ticket the miss belongs to. The phase is still in flight,
so the fix travels with it instead of becoming separate backlog. Once the phase has merged, this
option is gone — see "Gaps found after a phase has merged" under GitHub Issues.

Body (when there is one) explains **why**, not what — matches this repo's own commit-message
instruction in the personal CLAUDE.md. In this history the why is almost always evidence: what was
tried, what broke, what was verified live and how (`PLAN.md` §01 rule 1, "evidence over
assertion"). A `Verified ...` line describing an actual run against dev Postgres, a live endpoint,
or a built app is the norm for anything non-trivial, not an afterthought.

Merge commits keep git/GitHub's default message (`Merge branch 'x' into y`,
`Merge pull request #N from <owner>/<branch>`), sometimes with an added paragraph noting how a
conflict was resolved.

Claude Code-authored commits carry:
```
Co-Authored-By: Claude <model name> <noreply@anthropic.com>
Claude-Session: https://claude.ai/code/session_<id>
```
Leave these on commits Claude actually authored; don't add them to commits you write yourself.

## Pull requests

`Phase <phase>: <summary>` where `<phase>` matches a `PLAN.md` roadmap phase (`Phase 0`,
`Phase I`, `Phase II`, ...), optionally followed by the tickets it covers:

```
Phase I: vacancies API, filters, frontend (EM-11, EM-15, EM-16)
Phase 0: EM-45–51 rebuild sources schema, close Phase 0 spike gate
```

Two early PRs (#1, #7) used a `DEMO:` prefix ahead of throwaway/demo submissions for branches that
were later reopened properly (#2, #6) — not a convention to continue, just how those two got
superseded.

## GitHub Issues

Used rarely — Linear is the actual backlog (`PLAN.md`: "Linear holds the work items"). The two
GitHub issues in this repo's history exist only to mirror a specific Linear ticket into GitHub's
UI, titled `EM-<n>: <description>` matching the Linear ticket's own title, with GitHub's stock
labels (`bug`, `documentation`, `help wanted`, etc.) applied by nature of the work — no custom
label scheme. Don't create a GitHub issue as a substitute for a Linear ticket; only mirror one over
if there's a specific reason (e.g. surfacing it for portfolio visibility).

**Gaps found after a phase has merged.** If the miss belongs to a phase that has already landed on
`main` — no branch left to fix forward on — open a GitHub issue for it (`EM-<n>: <description>`,
same as any mirrored ticket), and name the phase it actually belongs to in the body (e.g. "Belongs
to Phase 0"), since the title alone won't show that once it's sitting in GitHub's current issue
list next to whatever phase is active now. This is the counterpart to "Gaps found while a phase is
still unmerged" under Commits — which of the two applies turns on whether that phase's branch has
ever been merged into `main`, not on when the gap was found.
